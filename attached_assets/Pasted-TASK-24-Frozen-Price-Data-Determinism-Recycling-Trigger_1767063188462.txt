PART A — PRICE CACHE POLICY (FULL DETERMINISM INCLUDING equity.csv)
===========================================================

Problem:
equity.csv varies across identical runs due to fresh API data changes / float differences. Rounding helps but cannot guarantee exact determinism when upstream data differs.

Goal:
Introduce a “frozen data” cache policy that guarantees the exact same OHLCV series is used for backtests when requested.

1) Add CLI flag: --price-cache-policy {AUTO,READONLY,REFRESH,OFF}
   Definitions:
   - AUTO: if cache exists for symbol+range, use it; else fetch once and write to cache
   - READONLY: ONLY read cache; if missing any required series -> raise a clear error and exit non-zero
   - REFRESH: always refetch and overwrite cache (then use it)
   - OFF: always fetch fresh without cache (current behavior)

2) Wire the policy into price loading:
   - Identify the single choke point where OHLCV is requested.
   - Ensure that for backtesting runs (--backtest or --backtest-v2), the policy defaults to AUTO (or keep current default OFF if you must preserve existing behavior, but support READONLY/REFRESH determinism modes).
   - Ensure the cache key includes: symbol, start/end, interval, auto_adjust flag if used, and any normalization settings.

3) Normalize stored data deterministically:
   - Store OHLC prices rounded to 2 decimals (or existing standard)
   - Store volume as int
   - Ensure index timezone / datetime normalization is consistent and stable.
   - Ensure read->write->read round trips produce identical frames.

4) Manifest integration:
   - In the run manifest, record the policy and whether data was fetched or fully cache-hit.
   - Add a small section like:
     price_data: {policy: READONLY, cache_hits: N, cache_misses: 0, source: yfinance, normalized: true}

PART B — RECYCLING MUST TRIGGER UNDER NON-BUDGET BLOCKS
===========================================================

Problem observed:
Even with forced settings (trigger ALWAYS, min_score_gap=0, min_hold=0, etc.), recycle_events_count stays 0. This strongly suggests recycling only triggers for “budget blocked” and ignores other constraint rejections (max positions, forming cap, cluster cap).

Goal:
Recycling should be considered whenever a candidate is rejected for ANY allocation constraint, depending on trigger mode:
- BUDGET_BLOCKED: only if blocked specifically by risk budget
- ALWAYS: if blocked by ANY constraint AND there exists a superior candidate worth considering

1) In allocator/entry logic, capture structured skip reasons:
   - blocked_by_budget
   - blocked_by_max_positions_total
   - blocked_by_max_positions_forming
   - blocked_by_cluster_cap
   - blocked_by_corr_cap (if used)
   - blocked_by_symbol_open
   - etc.

2) Define:
   blocked_any = any(blocked_by_*) EXCLUDING "symbol already open" (and any other non-actionable reasons)
   - (Keep symbol already open as a hard stop; recycling shouldn’t try to replace an existing symbol with itself.)

3) Trigger logic:
   - If recycle_trigger_mode == BUDGET_BLOCKED: only attempt recycle when blocked_by_budget == True
   - If recycle_trigger_mode == ALWAYS: attempt recycle when blocked_any == True

4) Ensure recycling events are recorded:
   - Whenever recycling sells/partially sells/exits a position and replaces with a new one, append an event record.
   - This record MUST include:
     date, old_symbol, new_symbol, action (PARTIAL/EXIT), freed_risk, used_risk, old_score, new_score,
     replacement_edge_r (if computed), old_future_r (if computed), and whether it was a “swap win”.
   - Ensure these events propagate into metrics.json -> recycling_effectiveness swap_edges array.

5) Make forced recycling possible for testing:
   - With settings:
     --recycle-trigger-mode ALWAYS
     --recycle-min-score-gap 0
     --recycle-min-hold-days 0
     --recycle-no-progress-days 0
     --recycle-no-progress-r 999
     --recycle-exclude-confirmed-winners false
